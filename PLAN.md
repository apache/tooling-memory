# Plan

Written 1 October 2026. The first target is a developer weekend on 10 and 11 October 2026: working code that a few people can run, read, and extend.

## What this is

The reference implementation of [Durable Memory for Disposable Agents](docs/durable-memory-for-disposable-agents.md). The paper designs shared memory and coordination for fleets of agents that outlive every component they are built from. This repository builds the smallest complete deployment of it, the one the paper's §14 asks for: one person's memory, one process, runnable on a laptop, and then grows it toward the stack in [docs/reference-stack.md](docs/reference-stack.md) without changing the surface.

The one piece of code that matters most is the **wrapper**: a per-session memory server that sits beside an agent harness, holds every credential and every policy check, and is the only thing the agent talks to. On a laptop it is a native binary that Claude Code or Codex reaches over MCP. In an institution the same binary runs as a sidecar the platform launches per workload. Same surface, same stores, different process boundary.

## Decisions already made

| Decision | Choice | Why |
|---|---|---|
| Language | Rust, one workspace | One core library compiles native for Windows and Linux, to wasm for a browser reader, and to WASI for sandboxed plugins. The Apache libraries involved (OpenDAL, DataFusion, Arrow, Iceberg) are Rust-native |
| The record | Markdown files with frontmatter, versioned, never edited in place | The paper's first principle: data outlives tooling, and a person with a text editor can read it |
| The engine | Not chosen. Local files through OpenDAL now; S3-compatible later | The paper names no engine, only seven guarantees (§4) |
| Partition key | The domain, everywhere | Record prefix, index shard, log partition, ledger schema. One writer per domain falls out of it |
| Local index and ledger | SQLite with FTS5, one file | Nothing to operate; BM25 ranking built in; rebuildable from the record |
| Agent binding | MCP over stdio first, HTTP second | Every harness speaks it; the surface in the paper's Appendix A is the contract |
| Policy | A grants file the owner edits; one principal | Identity is the serving layer's concern and a local server authenticates nobody (§5) |
| Interchange | A directory of entries plus a manifest with digests | Aligns with where the Open Memory Protocol work converges |
| Build speed | Cargo stays the developer loop and the source of truth for dependencies. Remote execution over the Remote Execution API is the direction for CI and shared caching, in preference to sccache, which is the interim: Bazel with rules_rust and crate_universe generated from the Cargo manifests, against a REAPI service (BuildBuddy, Buildbarn or NativeLink, the last written in Rust). Measured here: a clean build is 104 s cold and 39 s with a warm sccache; the dev target went from 27 GB to 2.2 GB on line-table debug info | A remote-execution build is content-addressed and shared across machines and CI, which a local compile cache is not. The cost is a second build description: generated, so it stays in step, but the native bits (bundled SQLite, ring) need toolchains declared. Spike before adopting: build the workspace under rules_rust against a local Buildbarn and compare |
| The gateway | LiteLLM's OpenAI-compatible API is the contract; llmao (`apache/tooling-llmao`) is the control plane in front of it, identity, PATs and project governance, and nothing of it is reimplemented here. `--auth gateway` speaks to any LiteLLM with a key: locally the compose stack with the master key, at the Foundation llm.apache.org with a PAT llmao issued. The egress's metering is per session and destination and sits beside LiteLLM's per-key spend, not instead of it | Duplicating a control plane would be the mistake; speaking its proxy's API is not. The local compose stands in for identity, which a laptop does not have |
| Containment | The harness runs with no network. Its only egress is the wrapper, over a unix socket relayed to loopback inside. The wrapper forwards model calls (to a gateway or a provider), checks the session label against the destination's ceiling first, reads token usage out of every response, and serves memory over MCP on the same socket. Linux: native namespaces, unprivileged. macOS: Seatbelt, not yet. Windows: WSL2 | Containment is the launcher's job and does not depend on how the harness authenticates. Metering and the model-class check come for free from being in the path, which is what a subscription login would otherwise lose |
| Handling by egress | A session's handling is capped at the ceiling of the destination its model calls go to, set at launch | A session whose calls go to a public-ceiling destination reads only public entries, so nothing it reads can leave above that ceiling |
| Credentials | The wrapper holds and injects them; the harness gets a placeholder. The one exception is a subscription login, which the harness must hold itself and the wrapper passes through | Anthropic requires the subscription be used by Claude Code itself. Codex with a ChatGPT login is not supported yet, since Codex routes that to chatgpt.com |
| The wrapper's reach | A confined process. It reads and writes only what is mounted into it: the record, its own state, its grants file. Nothing else on the host. Store and index roots are the mount points, and no name may become a path outside them | The agent beside it holds no credentials and the wrapper holds no ambient access. What is mounted is deliberate, as a container's mounts are, whether or not a container runtime is doing the confining |

## M0: the developer weekend, 10 and 11 October 2026

**What "working" means.** Someone clones this, builds it, points Claude Code at it, and the following happens:

1. `memory init` creates a domain with a grants file.
2. A session, through MCP, writes a handoff entry and a decision entry.
3. A **fresh** session starts, loads T0, finds the handoff, and continues the work without the transcript. This is the paper's first exit criterion (§14, M1).
4. `memory search` ranks results by BM25 and returns summaries first; `memory get` returns one body.
5. A task is created, claimed with a lease, heartbeated, and completed; a second claim while the lease holds is refused; an expired lease returns the task to the pool.
6. `memory export` writes a bundle; `memory import` lands it at raw and refuses to import the same entry twice.
7. Deleting the SQLite file and running `memory reindex` rebuilds index and ledger projection from the record alone.

Items 1 through 4 are the demo. Items 5 through 7 are what makes it the paper's design rather than a notes folder.

**Status, 1 October 2026.** All seven pass as `crates/memory/tests/cli.rs` against the
built binary, and `memory serve` answers a raw JSON-RPC session: initialize, sixteen
tools (`recall` among them since 3 October), a write under the session's author, the T0 resource. `local/` brings up LiteLLM
and Postgres in containers as the gateway, and `scripts/claude-via-llmao.sh` starts Claude
Code through it with the memory server attached. Left before the weekend: a run with a
real provider key and what happened written down; a one-page demo script; and whatever
that run turns up.

**In scope for M0**

- `core`: entry schema and frontmatter (id, type, domain, author, created, source, confidence, trust_tier, review_by, supersedes, classification), bundle manifest, digests, the label order.
- `store`: the record over OpenDAL's filesystem backend. Current version at `record/<domain>/<id>.md`, prior versions under `record/<domain>/.history/<id>/`. Demotion writes a tombstone; nothing is deleted in M0.
- `index`: SQLite FTS5 over title, summary, and body, plus a metadata table. Summaries-first results. Rebuildable.
- `ledger`: SQLite. `create_task`, `claim_next`, `claim`, `heartbeat`, `complete`, `release`. Leases expire by wall clock. Origin dedup on `(origin, upstream_event)`.
- `policy`: a TOML grants file: which domains the owner reads, each domain's default classification, each destination's ceiling. One principal.
- `server`: MCP over stdio exposing `search`, `get`, `write`, `create_task`, `claim_next`, `heartbeat`, `complete`, `release`, and T0 as a resource.
- `memory` binary: `init`, `write`, `search`, `get`, `t0`, `export`, `import`, `reindex`, `serve`.
- T0 generation: under 2k tokens, from the domain's handoffs, standing decisions, and pointers.

**Out of scope for M0, named so nobody builds it by accident**

- `recall`: landed early, 3 October, as M1's first cut: the pack with synthesis owed on a subscription login, a deputy through a key or the gateway otherwise; since 5 October the deputy and mining can take a route of their own, `--server-auth gateway`, so a harness on a personal login leaves the memory's calls to the institution. See the M1 row; what is left there is the real run.
- Erasure with receipts. M1. Demotion and tombstones are enough for M0.
- Classification enforcement on destinations beyond export. M1.
- HTTP binding, Postgres and Solr backends, Kafka log, WASI tap host, browser reader. M2 and later; see the stack document.

| M1, recall and erasure first cuts done 3 October | `recall`; erasure with stub and receipt; ceilings checked on every outbound call; HTTP binding. The last two hold already: the egress refuses a session label above the destination's ceiling before anything leaves, on every call, and `/mcp` on the egress is the memory server over MCP's streamable HTTP transport. Erasure, `memory erase <id> --reason <requested\|mistaken\|sensitive\|legal>`, is the paper's §4 in the small: the owner only, once per entry, and not on the MCP surface, since an irreversible action escalates to a person. The receipt is written first, naming the versions about to be removed and saying the erasure has not finished; a run that stops short, an index another process holds mid-query say, leaves that receipt and the next run finishes from it. The stub is written over the current version and over every archived one, so no version keeps the body; it keeps the frontmatter with `status: erased` and no summary, no title when the person asked or the material was sensitive, and for an erasure the person asked for, neither author nor sources. The index drops the row, re-indexes the stub, merges its full-text segments, vacuums and checkpoints its log, and says so when another connection kept the log from being truncated, so the body's bytes leave the file rather than wait to be overwritten; the record's status now wins over the index's row on every `get`, so a stub is never served because the index is behind. Entries that cite the erased one, in the body, the sources or as the entry superseded, are flagged with a review date of today for curation to re-derive or erase; the bundles served from the root for that domain are removed; the session's push note forgets the id. The receipt, `record/<domain>/.erasures/<id>.yaml`, is the erasure record and the coverage in one: who, the reason class, when, every version removed with the digest of the text it had, the ids flagged, and the copies out of reach named as unresolved: exports issued before, transcripts of sessions that read it, the queries kept in the read log, and the history and handoffs that are not scanned. The digests are consulted: `import` refuses an entry whose text a receipt in the target domain lists as removed, so a bundle exported before the erasure cannot bring the body back, and names it. Proven by tests that erase an entry a bundle and three citing entries hold and read every byte under the root with the read log on, re-import the older bundle, hold the index from another connection and finish on the second run, and refuse before the record step when the receipt cannot be written. An adversarial pass found the re-import, the unfinishable run, the vacuum that claimed what it had not done and the read log's queries; all four are fixed above. Not yet: entries written by sessions that read the erased one, which needs the read log to carry ids; erasure through a role policy on behalf of the person; a receipt that reaches an upstream host. Recall is three pieces. The pack: one function with no model behind it that turns a question, or a batch of queries, into the top hits with their sections and what they link to, inside a token budget, at one of two depths, summaries or sections; a message from the start, so the same object can arrive over a wire as well as from a local index. The deputy: a trait the server defines and the launcher implements over the egress, so the server never holds a credential; synthesis is one model call over the pack, and a second hop only when the model names what is missing, under a cap on hops, tokens and wall clock. The switch: which tier a session gets is its route, not an identity. A key or the gateway gives the server a model it may spend, so recall is server-executed, metered by the egress as a call of its own and checked against the destination's ceiling. A subscription login's credential is the harness's alone, so recall returns the pack with synthesis owed and the caller spends its one turn synthesizing; sampling through the harness is that same tier if a harness ever advertises it. Pull against push is observed, not asserted: two gets from one session inside a short window are a fan-out, and recall's default depth flips from sections to summaries once a session has shown one, since a serial caller pays a turn per section and a parallel one pays tokens only. The record serves every `get`; a per-session note of what packs pushed, by version, marks the gets that opened it, so pushed and then opened is counted in the funnel without a second serving path. Done: the pack, the deputy behind the egress with the destination's small default model, the fan-out rule, the cache, `recall` on the MCP surface and the CLI, `search` at section depth. The owed tier run here, 3 October, on a subscription credential with no deputy: Claude Code on Haiku, the server attached over stdio, a corpus of 57 entries seeded from the three docs. Asked to call `recall` once with a question about push against pull, it got a pack of eight at section depth, 5,190 tokens by the read log, followed the `next` field, answered in one turn citing the right entry, and its follow-up `get` was served from the session cache, which the log marks; the report's recall section shows both. A second session told to use only `search` and `get` chose `search` at section depth unprompted, wrote a keyword query that matched one entry, 1,987 tokens, and answered as well in the same number of turns. Two things follow. On a subscription login, owed recall and `search` with sections are nearly the same call, and recall's margin is the deputy, so the server-executed run with a key is the one that still matters. And the raw question is a wider query than the keywords a model writes: the pack from it cost two and a half times the single body the model's own query found, so a query reduction before the first search, or the deputy's second hop doing that work, is the first thing to try on that run. A golden suite says the same with a number instead of a reading: `memory golden golden/docs.toml` (`make golden`), fourteen questions over the docs corpus, each asked as written, stripped of stopwords, and by a hand-written keyword query standing in for a model's, scored through the pack with no model behind it; `--provider` scores the deputy's brief beside them. On the seeded corpus, hits in the top eight, mean reciprocal rank, and tokens a pack: the question as written 11 of 14, 0.65, 5,339; stripped 12 of 14, 0.75, 3,382; keywords 12 of 14, 0.86, 2,897. Dropping stopwords before the first search is therefore worth doing and gets most of the way to a model's query at under two thirds of the tokens; what it does not reach is the keyword query's ranking. Not yet: the key run, scored by that suite, and the deputy's prompt, the stopword reduction and the budgets tuned on it | The paper's §5 flow rules hold in one process, and the two recall tiers share every piece but the synthesis |

| M5d, to decide | What a handoff does to the task it was written for. Today a task the harness did not complete goes back to the pool unchanged with the handoff attached, and the next claimant reconciles the two. The alternative under discussion: a handoff spawns a continuation task whose body is what remains, pointing at the original with `continues`; the original leaves the pool as `continued`, neither claimable nor closed; completing the last link completes the chain, so the original is marked complete with the final handoff. When a chain dead-ends, after a bounded number of attempts or an explicit invalidation, the original is re-admitted with the chain's handoffs attached as lessons: its spec untouched, so the intent survives, and the attempts visible, so the next claimant starts from what was learned rather than from zero. Restoring it unchanged would throw the attempts away; amending its body would lose the original ask. Open: the attempt bound, whether a continuation inherits the original's requirements and priority, and how the ledger shows a chain | A task is a promise and a handoff is a report; keeping them distinct objects keeps both the intent and the history legible, which is what the record is for |

## The demo

`make demo`: a fresh record seeded with a few hundred entries from the decisions, the docs
and the paper; the savings report before any session; a task filed and admitted; a harness
claiming it, searching the record, answering with cited entries and completing it, confined
and metered; a recall of the same question twice, owed with no model behind it and
server-executed through the gateway when a key is there, so the tier switch is on screen;
the savings report after, with that session in the funnel and both recalls in the recall
section; the handoff it wrote. Then `make web` to show the same from a browser, and `make launch` for the
interactive session. Everything the paper claims about the read path appears as a measured
number next to the alternative it replaced.

## What a developer can pick up on the weekend

Each is a crate or a backend with a clear seam, and each can be done without touching the others.

- The `recall` deputy against a real corpus: the first cut is in (`crates/server/src/recall.rs`) and `memory golden` scores it; what is left is the key run, then the prompt, the stopword reduction and the budgets tuned on what the suite reports. A suite for your own domain is a TOML file beside `golden/docs.toml`.
- The HTTP binding of the same surface beyond the egress's `/mcp`: the launcher's reader and web terminal reaching a remote memory over it.
- A second `index` backend: Solr, or Tantivy embedded.
- A second `ledger` backend: Postgres with `SKIP LOCKED`.
- A second inbound tap beside GitHub issues (`taps/github-issues` is the pattern, `taps/github-comments` the outbound one): a tracker or a mailing list.
- The browser reader's next step: the page keeping a loaded bundle between visits, and admitting or refusing proposals from it.
- Conformance tests: a harness-neutral script that runs the seven M0 steps against any server exposing the surface.

## Working agreements

- Entries are the contract. Any change to the frontmatter is a change to `core` and gets a note in this file.
- Every crate has a test that round-trips its data through the record and back.
- The CLI and the MCP server call the same library functions; nothing lives only in the CLI.
- No engine-specific vocabulary in docs or code outside the backend that needs it.
