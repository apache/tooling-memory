# Plan

Rewritten 11 November 2026. The first plan was written on 1 October 2026 for a developer weekend on 10 and 11 October, and grew into a register of milestones. That register is kept as a record in [spikes/plan-2026-10](spikes/plan-2026-10/README.md); where another document cites a milestone by number (M4b, M5, M9), it means that register. This file now says where to find what is built, what the paper asks for that the code does not have, and in what order that gets built.

## What this is

The reference implementation of [Durable Memory for Disposable Agents](docs/durable-memory-for-disposable-agents.md). The paper designs shared memory and coordination for fleets of agents that outlive every component they are built from. This repository builds the smallest complete deployment of it: one person's memory, one process, runnable on a laptop. It then grows toward the stack in [docs/reference-stack.md](docs/reference-stack.md) without changing the surface.

The one piece of code that matters most is the **wrapper**: a per-session memory server that sits beside an agent harness, holds every credential and every policy check, and is the only thing the agent talks to. On a laptop it is a native binary that a harness reaches over MCP. In an institution the same binary runs as a sidecar the platform launches per workload. Same surface, same stores, different process boundary.

## Decisions already made

| Decision | Choice | Why |
|---|---|---|
| Language | Rust, one workspace | One core library compiles native for Windows and Linux, to wasm for a browser reader, and to WASI for sandboxed plugins. The Apache libraries involved (OpenDAL, DataFusion, Arrow, Iceberg) are Rust-native |
| The record | Markdown files with frontmatter, versioned, never edited in place | The paper's first principle: data outlives tooling, and a person with a text editor can read it |
| The engine | Not chosen. Local files through OpenDAL now; S3-compatible later | The paper names no engine, only seven guarantees (§3) |
| Partition key | The domain, everywhere | Record prefix, index shard, log partition, ledger schema. One writer per domain falls out of it |
| Local index and ledger | SQLite with FTS5, one file | Nothing to operate; BM25 ranking built in; rebuildable from the record |
| Agent binding | MCP over stdio first, HTTP second | Every harness speaks it; the surface in the paper's Appendix A is the contract |
| Policy | A grants file the owner edits; one principal | Identity is the serving layer's concern and a local server authenticates nobody (§6) |
| Interchange | A directory of entries plus a manifest with digests | Aligns with where the Open Memory Protocol work converges |
| `review_by` on disk | A calendar date, `review_by: 2027-04-01`. A binary reads that and the year-and-day list that binaries before this change wrote; it writes only the date. The bundle format stayed `durable-memory/bundle/0` for this change; the `cites` row below made it `bundle/1` | The date is the shape the paper always gave, and the list was `time`'s default, not a choice. Every record on disk still reads. An older binary cannot read an entry a newer one wrote with a `review_by`, so upgrade every binary that shares a record or takes its bundles. `amem log materialize` compares the log with the stored text, not a re-render, so a record written in the old shape is not reported behind |
| `cites`, curator, auditor | The frontmatter field `source` is `cites`, as the paper's Appendix A names it; `amem librarian` is `amem curator`, `amem check` is `amem audit`, and task origins are `curator:<kind>` and `auditor:<kind>`. The bundle format is `durable-memory/bundle/1`. No alias: a binary refuses an entry that carries `source`, and refuses a `bundle/0` | The paper settled on these words, and a demo that says librarian where the paper says curator reads as a different design. There are no users yet, so a clean break costs a reseed (`make demo-ready RESET=1`). A silent read of the old field would drop an entry's citations, so the parser refuses it in words |
| Build speed | Cargo stays the developer loop and the source of truth for dependencies. Remote execution over the Remote Execution API is the direction for CI and shared caching, in preference to sccache, which is the interim: Bazel with rules_rust and crate_universe generated from the Cargo manifests, against a REAPI service (BuildBuddy, Buildbarn or NativeLink, the last written in Rust). Measured here: a clean build is 104 s cold and 39 s with a warm sccache; the dev target went from 27 GB to 2.2 GB on line-table debug info | A remote-execution build is content-addressed and shared across machines and CI, which a local compile cache is not. The cost is a second build description: generated, so it stays in step, but the native bits (bundled SQLite, ring) need toolchains declared. Spike before adopting: build the workspace under rules_rust against a local Buildbarn and compare |
| The gateway | LiteLLM's OpenAI-compatible API is the contract; llmao (`apache/tooling-llmao`) is the control plane in front of it, identity, PATs and project governance, and nothing of it is reimplemented here. `--auth gateway` speaks to any LiteLLM with a key: locally the compose stack with the master key, at the Foundation llm.apache.org with a PAT llmao issued. The egress's metering is per session and destination and sits beside LiteLLM's per-key spend, not instead of it | Duplicating a control plane would be the mistake; speaking its proxy's API is not. The local compose stands in for identity, which a laptop does not have |
| Containment | The harness runs with no network. Its only egress is the wrapper, over a unix socket relayed to loopback inside. The wrapper forwards model calls (to a gateway or a provider), checks the session label against the destination's ceiling first, reads token usage out of every response, and serves memory over MCP on the same socket. Linux: native namespaces, unprivileged. macOS: Seatbelt, dry-coded and not yet run on a Mac. Windows: WSL2 | Containment is the launcher's job and does not depend on how the harness authenticates. Metering and the model-class check come for free from being in the path, which is what a subscription login would otherwise lose |
| Handling by egress | A session's handling is capped at the ceiling of the destination its model calls go to, set at launch | A session whose calls go to a public-ceiling destination reads only public entries, so nothing it reads can leave above that ceiling |
| Credentials | The wrapper holds and injects them; the harness gets a placeholder. The one exception is a subscription login, which the harness must hold itself and the wrapper passes through | Anthropic requires the subscription be used by Claude Code itself. Codex with a ChatGPT login is not supported yet, since Codex routes that to chatgpt.com |
| The wrapper's reach | A confined process. It reads and writes only what is mounted into it: the record, its own state, its grants file. Nothing else on the host. Store and index roots are the mount points, and no name may become a path outside them | The agent beside it holds no credentials and the wrapper holds no ambient access. What is mounted is deliberate, as a container's mounts are, whether or not a container runtime is doing the confining |
| Proof of concept, and the production shape (M2) | Everything built so far proves the contracts on the simplest stores that hold them on one laptop: files, SQLite, JSONL, one process, one host. It stays that way as the reference, and production backends go in behind the same crates, one store at a time, each proven against the unchanged conformance suite and measured with the evaluation harness and `amem savings` before it is preferred. The targets are the reference stack's: the ledger in PostgreSQL, one schema per domain, a claim as one row-locked statement, first, since it is the contended path; telemetry as OpenTelemetry spans from the egress (model calls), the server (reads) and the ledger (task transitions) into a collector, beside the SQLite tables until the librarian's signals are computed from the stream, then instead of them; the index in Solr sharded by domain; the record in an object store with versioning through OpenDAL; the curation cycle event-driven off the log. A backend is selected by configuration in the root, never by a build flag, so one binary is the laptop and the sidecar | A proof of concept that is honest about being one can be judged on the contracts, and a production move that has to pass the same suite cannot quietly change them. The ledger first because ten thousand committers and a fleet claiming around the clock contend there and nowhere else on the hot path. OpenTelemetry because the librarian's signals, cost per task and the watch on the watchers are analytics, and the reference stack already puts them on a stream rather than in the record |
| Policy and the perimeter (M12) | The checkable perimeter is Rego from the first day: the built-in policy ships in the policy crate and runs in process through regorus with the grants file as data, a root may replace it under `policy/*.rego`, and at scale the same files run in OPA as a sidecar with partial evaluation compiling the read filter into the index query. Its scope is the paper's: access, admission, spend and blast-radius gates, irreversibility; judgement is never encoded. Admission scales with what a task asks for: the system's own filings and a session's filings from a held task within that task's requirements are admitted where the domain admits its own, inflated requirements and filings on a session's own account stay proposed. Writes are scanned for what is not knowledge, instructions to the reader, broadcast to agents, tool syntax, hidden text, payloads, secrets, and from anyone but the owner such a body is quarantined for the owner, never served; a verified entry is replaced by no one but the owner; an agent session past the supersede count in `[gates]` is stopped. Every decision is logged with the policy version. Detection reads the logs, not the record: a write log beside the read log, `amem taint` for an entry's reach, and write-rate and relay alarms in the librarian's telemetry | Shared memory is an injection surface and a channel, and the paper's defence is structural: data is not authorization, the perimeter is outside the loop, and gates scale with blast radius. Rego from the start means the laptop and the fleet check the same rules, and a policy that is text in the record can be reviewed, versioned and cited by a decision log |
| Tasks and their relations (M5d) | The model stays tasks, leases, handoffs and `depends_on`; relations are expressed in fields that exist, no coordinator process. A subagent task the board files carries `origin: task:<parent>`, so a child knows its parent and the tree is a query. When the board refuses a spawn it also files a continuation, "resume `<parent>` with what the children found", with `depends_on` naming the children and `origin: continues:<parent>`; the parent's run ends with its handoff as today, and the parent waits on the board, claimable by nobody while a continuation of it is open (decided 12 October, after act 4 of the demo showed it claimable and so done twice); the continuation's completion completes the parent with the same handoff, and its parent in turn, up the chain, unless a holder with a live lease has it; a continuation invalidated without a successor leaves the parent claimable again; and the continuation becomes claimable when the last child completes, with every child handoff and the parent's own in its prompt, which the prompt builder already does for `depends_on`. Fan-in is therefore the existing dependency rule; fan-out is filing; a chain is a sequence of continuations, each a task on the board, held by no process. Dedup at filing is `origin` plus a hash of the prompt, so the same spawn asked twice is one task. Admission is by rule: a domain grant admits tasks a session files from its own task, and the human stays in the loop for tasks from outside, a tap's say. No depth cap: a tree may be as deep as the work needs, and a step that only a person can take, a task whose requirements match a human principal, is a node like any other, so a human's answer sits in the chain and adds to its depth as a matter of course. Invalidation is recursive: deprecating a task deprecates its subtree, the children still open and the continuations that depend on them, each marked `superseded_by` the invalidation, and a dead end re-admits the root with the chain's handoffs attached as lessons, as M5d's register row says. Artifacts are entries, typed and labelled, written by the task that produced them and cited by its handoff; no new table. Memory written by a child is visible to the parent as it is to any session, through search, recall and T0; no push to a running agent, since no harness takes one and a run that needed a child's result before finishing should have been a continuation. The board is visible: the web terminal gets a page of tasks by status with their tree, where a human claims the tasks addressed to them | A task is a promise and a handoff is a report; a continuation is a new promise made from a report. Keeping them separate objects keeps intent and history legible, and keeping relations in `origin` and `depends_on` means nothing new has to be invented, only named. A depth cap would have been a guess at how work decomposes; the paper's answer is solvability, every leaf matches someone, and humans are claimants |
| Bundle records and `highest_label` | A bundle's `highest_label` counts its promotion records with its entries, and `manifest::FORMAT` stayed `bundle/0` for this change; the `cites` row made it `bundle/1` | There are no users yet, so the meaning of a field may change without a version bump. A reader from before the records refuses only a bundle whose records sit above all of its entries, which is the safe side: it never accepts more than before |

## Where the code stands

The contracts of the read path, the ledger's first rules, the perimeter and the evaluation tools are built and run end to end on ten harnesses; [README.md](README.md) lists them, with what is missing and what works only at demo scale. Each backend is the simplest one that holds its contract on one laptop.

The paper moved after most of that code was written. In the first ten days of November 2026 it gained positions, task definitions, a rule lifecycle, approvals as events, autonomy levels, the measures against a fleet that turns inward (upkeep share, induced work, a landing queue), a "Measured by" column on every evidence row (Appendix G), and an inventory of its own size (Appendix H). Appendix H's "Described only" column is the paper's own list of what has no code. The table below is that list, widened by a read of every section against the code on 11 November, and put in build order.

## Toward the production shape

Nothing above changes a backend. [docs/reference-stack.md](docs/reference-stack.md) says what each one becomes; this is the order, each step behind the trait or seam that exists today.

1. The ledger on PostgreSQL with a pool, as a projection of the log. The schema per domain and the `SKIP LOCKED` claim are built.
2. Telemetry as OpenTelemetry spans into a collector and analytics tables. The spans are built; the metrics of package 12 then read tables, not whole files.
3. The index in a search engine sharded by domain, with the read filter compiled into its query.
4. The record in a versioned object store, through OpenDAL.
5. The event log on a broker: the ledger's events in it, the index fed as it grows, a freshness lane with a published bound.
6. Curation driven by log events, not by a survey of the whole record.
7. The policy engine as a sidecar with partial evaluation.
8. The memory server apart from the egress, with a network binding upstream.
9. Identity: principals that authenticate, and the principal chain in a short-lived token.
10. Hosted tools registered in the gateway.
11. The recall deputy, the curators and the auditors as agents on the platform that already runs agents.
12. A reference compose file for the whole stack.

The paper adds a condition on every step here: each package above has to hold on the production backend too. Appendix G names a metric or a drill as the measure for 51 of its rows; `amem` computes a few of those metrics today, and no drill runs.

## The demo

`make demo-all HARNESS=<harness>` plays eleven acts on one record: the read path; curation and the trust tiers; the perimeter; the task fabric; watching it; memory against no memory; the platform; running a session again; from outside; the record moves; and what this is not, yet. [docs/demo-narrative.md](docs/demo-narrative.md) narrates them. Act 11 prints README's two lists, so the demo cannot claim more than the code has. Each package above ends with its line removed from those lists and a step in an act.

## Working agreements

- Entries are the contract. Any change to the frontmatter is a change to `core` and gets a row in "Decisions already made".
- Every crate has a test that round-trips its data through the record and back.
- The command line and the memory server call the same library functions; nothing lives only in the binary.
- No engine-specific vocabulary in docs or code outside the backend that needs it.
- A package changes the code, its demo step, README's lists and this file's table in one pull request.
